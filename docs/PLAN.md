# Frict

Self-hosted push 2FA for Authentik. Named after the *phryctoria*, the ancient
Greek chain of fire-beacon towers that relayed signals across the land.

GitHub org `frict-auth`: `frict-server`, `frict-android`, later `frict-ios`.
Domain `frict.app`; Android application ID `app.frict.android`.

Plan v1 — 2026-10-30. Status: M0 done (GO); M1 in progress.

---

## Goal

A push notification on your phone asks "Approve sign-in to X from IP Y?". You
approve with a fingerprint, and Authentik logs you in. Everything is
self-hosted: no Cisco/Duo account, no third-party push gateway beyond FCM/APNs.

- Android first. iOS later (deferred, see M6).
- TOTP stays as the backup factor; WebAuthn stays as the phishing-resistant one.
- Practice ground was chat-relay / chat-android; this project reuses their
  code, CI and lessons.

### Out of scope for v1

- **Number matching.** Not possible through the Duo shim (Authentik puts
  nothing from our server on the login page). Consequence, stated plainly:
  Frict does **not** meet NIST SP 800-63B-4 §3.1.3.1 for push
  authenticators and is vulnerable to push bombing in CISA's terms. Accepted
  for household use; mitigated by request context, push rate limits, an
  automatic pause, and alerts (see Safeguards).
- Phishing resistance (no push scheme has it; WebAuthn covers that).
- A native/forked Authentik stage.
- De-Googled transport (UnifiedPush/ntfy) — later.
- Multiple devices per user.

## Architecture

### Integration: Frict speaks Duo's Auth API

Authentik's existing Duo stage talks to our server instead of Duo. Authentik
itself is unchanged, and the LDAP outpost already passes Duo push through.

- The Duo stage's API hostname is a free-text field.
- Authentik calls only `/auth/v2/enroll`, `/auth/v2/enroll_status`, and
  `/auth/v2/auth` (push). Requests are HMAC-signed (sig v5) with the stage's
  client secret; Frict verifies them.
- The enrollment QR code and activation link are generated by Frict, so they
  point at our app.
- `/auth` blocks until the user answers. Authentik answers HTTP 408 after
  about 213 s (measured with a 240 s hold, M0 (c′)); the ~215 s cause, its Rust
  front server's `timeout_http_*` settings adding up, is inferred from source.
  Frict enforces its own expiry (60–120 s), well inside that.
- The Duo stage's only settings are client ID, client secret, API hostname and
  two admin keys. Nothing else — including alerting — is configurable from
  Authentik.

Known Authentik quirks: the UI says "Duo" everywhere; a user with a Duo device
is always offered it over TOTP (#22816).

### Components

- **`frict-server` (Go, stdlib + `golang.org/x/oauth2`).** chat-relay grown up.
  - Duo-compatible endpoints for Authentik.
  - Device endpoints: enrollment, challenge fetch, signed answer, FID
    registration.
  - SQLite store, same pattern as chat-relay (schema version, migrations
    tested against a copy of the prior schema).
  - FCM HTTP v1 sender behind an interface (code from chat-relay #9).
- **`frict-android` (Kotlin/Compose).** New app built from chat-android's
  skeleton: FID registration, Keystore-backed storage, single-threaded account
  operations, emulator scripts.

### Enrollment

1. Authentik's Duo setup stage shows a QR code generated by Frict.
2. The app scans it and creates two non-exportable **P-256 keys in
   StrongBox/TEE**: an `approval_key` requiring biometric auth on every use,
   which signs only answers, and a `device_key` with no user auth, which
   signs background requests (challenge fetch, poll, FID update). (P-256 is
   the only algorithm both Android StrongBox and the iOS Secure Enclave
   support in hardware.) Details in `docs/device-protocol.md`.
3. The app sends both public keys, their key attestations and its FID.
4. `enroll_status` reports success.

### Login

1. Authentik calls `/auth`, which blocks.
2. Frict creates a challenge: opaque 128-bit ID, single use, expires in
   60–120 s.
3. The FCM data message carries **only the challenge ID**. Google never sees
   who is logging in to what.
4. The app fetches details with a device-signed request and shows app, IP,
   user and time.
5. The user approves, or denies with a reason ("I didn't start this" /
   "cancel"). The app signs the answer.
6. Frict verifies the signature and answers Authentik.
7. If the push doesn't arrive, the app can poll for pending challenges.

### Safeguards

- From CIBA: opaque single-use IDs, expiry, server-set poll interval.
- From privacyIDEA: keys exchanged at enrollment, signatures in both
  directions, a reason on every deny, poll fallback.
- From NIST 800-63B-4: cap on pushes since the last successful login; a
  failed-attempt counter that a new challenge does not reset. Decisions:
  - Push cap: a total since the last successful login; once it is reached,
    one push per `FRICT_PUSH_COOLDOWN`, so the lock lifts by itself
    (§3.1.3.2 limit; §3.2.2 waiting-period technique).
  - Failed attempts: denies and timeouts, not reset by a new challenge,
    reset only by a successful login on that device; at `FRICT_MAX_FAILED`
    (at most 100) the device is disabled (§3.1.3.2, §3.2.2).
    `FRICT_MAX_FAILED` is a live threshold: raising it re-enables devices
    disabled under the old limit.
  - Recovery from a disabled device: an Authentik admin deletes the user's
    Duo device and the user re-enrolls, which gives a new Frict user with
    fresh counters. Frict has no admin tool (§3.2.2 "disabling that
    authenticator").
- **"I didn't start this" means the user's password is compromised** (the push
  only happens after the password step). On that deny Frict:
  1. Automatically pauses pushes for that user for N minutes (stops push
     bombing with no human action).
  2. Sends a high-priority alert to the approver app of every user in the
     server's `alert_recipients` config (default: the admin):
     > Someone has geoffrey's password. Sign-in to Grafana from 203.0.113.7
     > at 14:02 was denied. [Reset password] [Revoke sessions]

     The buttons are deep links into Authentik's admin UI, so Frict holds no
     Authentik admin token.

  Authentik's own event log tells them apart: its `login_failed` event
  records `duo_response.status` `fraud` for "I didn't start this" and `deny`
  for "cancel" (`e2e/login_test.go`).

  Limits, all set in frict-server's environment (`cmd/frict-server/main.go`):

  | Setting | Default | Why |
  |---|---|---|
  | `FRICT_PUSH_CAP` | 10 | A person rarely needs more than a few tries per login; 10 leaves room for a missed push or two. |
  | `FRICT_PUSH_COOLDOWN` | 15 min | Holds a push bomber to 4 pushes an hour, inside §3.2.2's "30 seconds up to an hour". |
  | `FRICT_MAX_FAILED` | 20 | Twice the cap and well under §3.2.2's 100, so ignoring pushes alone can't disable a device within a day. |
  | `FRICT_PAUSE` | 30 min | Long enough for an admin to read the alert and reset the password, short enough that a mistaken tap doesn't lock the user out for the day. |
  | `FRICT_ALERT_RECIPIENTS` | `akadmin` | Authentik's bootstrap admin username. |
  | `FRICT_ALERT_TTL` | 24 h | A phone that was off overnight still gets the alert on its next poll. |
  | `FRICT_AUTHENTIK_URL` | none (required) | Base of the alert links. |

  When a safeguard refuses a push, `/auth` answers `deny` with Duo's
  `locked_out` status ("The user has been disabled due to authentication
  failures", duo.com/docs/authapi) and says which safeguard in `status_msg`;
  Authentik records both in `login_failed`. A refused `/auth` sends no push
  and counts as neither a push nor a failed attempt.

  Authentik 2026.8.5's `/auth` call supplies the alert's fields
  (`authenticator_validate/challenge.py:267-290`): `display_username` (the
  Authentik username), `ipaddr` (the client IP), `pushinfo` with `Domain`
  (the login host) and `Application` (only when the flow was started for an
  application), and `type` ("<brand> Login request"). It sends no time;
  Frict records when the push was created and when it was reported.

  Authentik's admin UI has no per-action URL, and a user's page needs the
  user's primary key, which Frict can't look up without an API token. Both
  buttons open the admin user list filtered to that username, whose row
  holds "Set password", "Create recovery link" and the "Revoke Sessions"
  action.

### TLS: getting past Duo's certificate pinning

`duo_client` (Duo's Python library, used by Authentik) trusts only its own
bundle of 15 roots. ISRG (Let's Encrypt) is not among them. Authentik passes
no CA option, so the bundle is always used.

- **Route A (chosen): Let's Encrypt, with the system CA bundle mounted over
  `duo_client`'s `ca_certs.pem`** in the Authentik server and worker. In
  production the mounted file is the host's
  `/etc/ssl/certs/ca-certificates.crt`, kept current by the host's
  `ca-certificates` package. Dev and e2e copy the Authentik image's own
  `/etc/ssl/certs/ca-certificates.crt` out of the image instead. Proven in
  M0: inside the 2026.8.5 image (`duo_client` 5.6.1) a `duo_client` call to
  a Let's Encrypt host completes the handshake with the mount and fails
  certificate verification without it (`docs/m0-findings.md` (b)). The
  mount target contains the Python version
  (`/ak-root/.venv/lib/python3.14/site-packages/duo_client/ca_certs.pem`) and
  silently stops applying when it changes, hence the deploy check.
- **Deploy check:** `scripts/duo-tls-check.sh <container> https://api.frict.app`
  runs `duo_client`, as Authentik calls it, inside the running server and
  worker, and exits non-zero on any TLS or connection failure. CI runs the
  same check against the e2e stack's frict-server. Runbook in the appendix.
- **Fallback B: AWS ACM certificates via its ACME endpoint.** Every ACM chain
  ends at Amazon Root CA 1–4 or Starfield Services G2, all in Duo's bundle, so
  no mount is needed. About $1 per issuance, 45-day certificates, stock
  certbot with EAB. Not tested end to end.
- **Tried and failed: Google Trust Services.** The GTS certificate for
  `api.frict.app` chained to GTS Root R1, which Duo's bundle lacks, and GTS
  rotates intermediates outside the client's control (`docs/m0-findings.md`
  (b)).
- **Upstream:** `duo_client` 5.7.0 has `disable_ca_pinning`, which uses the
  system trust store with verification still on, and Authentik `main`
  already pins 5.7.0. The ask is a per-stage Duo option that passes it
  through; it would make the mount unnecessary. Open an issue first: the
  heavier PR #25041 was closed without explanation. Filed under Geoffrey's
  name; an agent drafts the text.

## Ways of working

Carried over from chat-relay / chat-android.

### Review and merge

- One PR per task. Every PR is reviewed by a **different vendor** than the
  one that wrote it.
- **The human is not a merge blocker.** Each repo:
  - Auto-merge enabled; the implementer turns it on when opening the PR.
  - Ruleset requires CI **and** a `cross-review` commit status; no required
    approvals.
  - The `cross-review` status is pinned to a dedicated GitHub App, so a status
    from any other token blocks the merge. It is posted only when a
    different-vendor review passes. This stops an implementer stamping its own
    PR; it is a process guard, not a defence against the orchestrator.
  - Merge deploys; the post-deploy check can still fail the deploy.
- Changes to **prod Authentik** stay manual, by Geoffrey.
- **The bar for blocking a PR is set at dispatch**, in the review brief, not
  discovered in round 6 (lesson from chat-android #3).
- Reviewer availability: Codex out until 2026-11-25. Until then Pi on
  DeepSeek is the only non-Claude reviewer. Updating `agy` adds Gemini.

### Evidence and checks

- Checks are allowed to fail: no `|| true`, no swallowed diagnostics. Image
  digest and `/healthz` are checked after every deploy.
- Evidence is raw logs saved to files, never retyped summaries.
- A test is not trusted until shown to fail when the code is broken (mutation
  checks, negative controls).
- A check that fails without explaining why is broken; capture enough to
  diagnose it (see chat-android's emulator failure capture).

### Domain lessons

- Use Firebase Installation IDs (FIDs), not FCM registration tokens.
- A dead FID clears only the device ID, never the user's claim.
- Credentials are read from an explicit file, never from ambient credentials.
- Single-threaded account operations on the device; no stored-state races.
- Don't log tokens, keys or message bodies.

### Secrets

- Secrets live only on the box. Refer to them by path in plain words — a bare
  path at the end of a message can get attached as a file.
- `.gitignore` covers `secrets/` from the first commit.
- Secret scanning push protection on.

### Agent hygiene

- Agents **append** to shared memory files; they never rewrite them. (Two
  agents rewriting `project_chat_app.md` concurrently wiped each other's
  notes.)

## Test strategy

### Walking skeleton, not red-until-done

- M0's spike becomes the first e2e test: Authentik in compose plus a stub
  Duo server that approves everything. It passes on day one because it
  asserts only what exists.
- Each later PR tightens that test as it adds the feature (the stub becomes a
  fake phone that signs; deny, timeout and replay cases land with their code).
- Unit tests land with the code they cover (sig v5 verification, challenge
  state machine, store, rate limits).
- No skip/xfail placeholders. `main` is always green.

### Tiers

1. **Unit.** Go with `-race`; Android JVM tests with the fake-server pattern
   from chat-android #3.
2. **Server e2e, no phone.** Compose stack: Authentik pinned to 2026.8.x and
   bootstrapped via `AUTHENTIK_BOOTSTRAP_*`, frict-server, and a scripted
   fake phone in Go with its own P-256 keys. A Go test logs in through
   Authentik's flow-executor API (no browser). Covers approve, deny, timeout,
   replay, bad signature. A test CA is mounted over `duo_client`'s bundle in
   the worker.
3. **LDAP e2e.** `ldapsearch` bind through the outpost in the same stack.
4. **Live FCM.**
   - Every PR, server side: a contract test sends through real FCM with
     `validate_only: true` (validates without delivering — *unverified*),
     authenticated by keyless WIF.
   - Every PR, device side: real FCM push to an emulator on a KVM-enabled
     GitHub runner, using chat-android's scripts. If the cold-boot
     `AUTHENTICATION_FAILED` retry flakes, fix it; don't mark it
     non-blocking.
5. **Real-phone acceptance, once per milestone.** Doze wake-up, hardware-backed
   key with attestation, real fingerprint.

fails (fall back to a forked stage). If (d) or (e) fails, LDAP drops out of

biometric approve, poll fallback, alert display. Proven by emulator e2e, then
a real phone.

**M3 — Deploy.** Server on the Hetzner box. In prod Authentik, a dedicated
test user and flow get a Duo stage pointing at Frict. Then Geoffrey.

**M4 — Hardening.** Attestation verified against Google's root; re-enrollment

**M5 — LDAP / Linux login.** Only if M0 said yes.

## Production setup

Server hostname: **`api.frict.app`**. This is the "API hostname" typed into
Authentik's Duo stage and the host the app talks to.

Frict runs on the same Hetzner box as Authentik (`91.99.109.112`, nginx in
front). Authentik's worker reaches Frict through the public hostname, so
traffic leaves the container and comes back in through nginx on the same
host.

### Cloudflare DNS (zone `frict.app`)

| Type | Name | Content | Proxy |
|---|---|---|---|
| A | `api` | `91.99.109.112` | **DNS only (grey cloud)** |
| CAA | `frict.app` | `0 issue "letsencrypt.org"` | — |
| CAA | `frict.app` | `0 iodef "mailto:<you>"` | — |

- **Grey cloud is mandatory.** A proxied (orange) record makes Cloudflare
  terminate TLS with its own certificate, which Duo's pinning will reject
  or accept unpredictably. Same model as `auth.itsalwaysreefreemas.org`.
- CAA is less restrictive than it looks. Per Cloudflare's docs (not tested
  here), with Universal SSL, adding any CAA record makes Cloudflare add CAA
  records for the CAs it issues Universal certificates from, and that list
  changes over time
  ([CAA records](https://developers.cloudflare.com/ssl/edge-certificates/caa-records/)).
- Enable DNSSEC on the zone. Per Cloudflare's docs (not tested here), it is
  one click on Cloudflare Registrar, where `frict.app` is, because Cloudflare
  publishes the DS record itself (taking one to two days); with another
  registrar the DS record is added there by hand
  ([DNSSEC](https://developers.cloudflare.com/dns/dnssec/),
  [Registrar DNSSEC](https://developers.cloudflare.com/registrar/get-started/enable-dnssec/)).
- `.app` is on the HSTS preload list: every `*.frict.app` host must serve
  HTTPS. Nothing else is needed for `api.`.
- Nothing at the apex or `www` yet.

### Hetzner box

- nginx vhost `api.frict.app` → `127.0.0.1:<port>`. Container bound to
  loopback only.
- Let's Encrypt certificate for `api.frict.app`, alongside `auth.` and
  `chat-relay.`.
- Authentik server and worker: the host's system CA bundle mounted over
  `duo_client`'s `ca_certs.pem` (appendix).
- `/home/deploy/frict/{data,secrets}` owned by uid 65532; FCM key at
  `secrets/fcm-sa.json`, mode 0400.
- Deploy check: `scripts/duo-tls-check.sh` against `https://api.frict.app`
  in the Authentik server and worker (appendix).

## Appendix: TLS route A runbook

**1. Certificate.** Let's Encrypt for `api.frict.app` with certbot's nginx
plugin, as for `auth.` and `chat-relay.`. The CAA records in "Production
setup" must exist first.

**2. Mount, checked on every Authentik image upgrade.** Mount the host's
`/etc/ssl/certs/ca-certificates.crt` (kept current by the host's
`ca-certificates` package) over `duo_client`'s bundle in **both** the server
and the worker. Read the target path from the installed package rather than
assuming it; it changes with the image's Python version:
```bash
IMAGE=ghcr.io/goauthentik/server:<version>@sha256:<digest>
docker run --rm --entrypoint python "$IMAGE" \
  -c 'import duo_client.client as c; print(c.DEFAULT_CA_CERTS)'
```
```yaml
    volumes:
      - /etc/ssl/certs/ca-certificates.crt:<DEFAULT_CA_CERTS printed above>:ro
```

**3. Deploy check, after every Authentik or certificate change.** Fails on
any TLS or connection error; any HTTP status is a pass.
```bash
scripts/duo-tls-check.sh <server container> https://api.frict.app
scripts/duo-tls-check.sh <worker container> https://api.frict.app
```

**Fallback B (AWS ACM via ACME):** create an ACM ACME endpoint, add its
validation CNAME in Cloudflare, add an `amazon.com` CAA record, register
certbot against the endpoint with its EAB key, and drop the mount. The deploy
check stays. Not tested end to end.
